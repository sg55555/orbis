# Orbis 地域プロフィール 再設計 — 地政学的分析レポート化（Phase 2.5c 直前）

## 0. サマリ（一段落）

ドリルダウンの地域プロフィールを、現状の「観光ガイド的な紹介（概要/気候/特産/産業/交通/観光）」から、**地域を"因果の連鎖"で読み解く、根拠つきの地政学的分析レポート**へ再設計する。太田さんの要望は5点：①地政学的要素、②産業発展の経緯として立地・気候がどう関わったか（＋近代化のスピード）、③現在の外交姿勢とその背景、④AIが何をエビデンスにどう判断したかの明示、⑤自分で分析するとき"どこを見ればいいか"が見える構造。この再設計は 2.5c（実LLM生成）の**直前**に行い、生成前に項目を確定する（生成後に項目を変えると全件再課金になるため）。実装済みのパイプライン/UI/配線（2.5b・本番 main c52e3ae/SW v49）はデータ中身がダミー。本 spec が確定した項目で 2.5c を生成する。

## 1. 背景

- 2.5b までダミーデータで本番 LIVE（コード/UI/配線/データ配線は稼働済み）。2.5c は「データ中身の差替」だが、太田さんFB①「フロート内の項目を精査したい」を受けて**項目自体を再設計**する（＝差替でなく再構築）。
- 現状の情報源は ja Wikipedia の REST 要約（extract＝1〜3文）＋ Wikidata の数値のみ。この深さでは地政学・外交・因果は**根本的に書けない**。情報源の刷新が本設計の前提。
- 進め方は max で設計を詰め切り（本 spec）、実装は xhigh + workflow。段階導入（アジアから）。

## 2. ゴール / 非ゴール

**ゴール**
- 地域を「地勢→産業の成り立ち→社会→地政→外交」の因果で読める分析レポート。
- 各主張の**確度**（確実／推定／要鮮度）と**根拠**、そして**自分で深掘りする足場**を明示する。
- カテゴリ要約でなく**固有名を列挙**する（言語名・宗教名・産業名・隣接国名）。
- 近代化のスピードを**年表**で見せる。
- レベル（国/県/都市）に応じて項目を適切に縮退する。

**非ゴール（YAGNI）**
- 因果マップ（矢印図）などの図解 → 将来オプション（複雑度・検証コスト）。年表は採用。
- 外交の"時々刻々の最新動向"の追跡（Web検索・定期再生成）→ 静的配信の利点を保つため入れない。構造的立場＋要鮮度ラベルで扱う。
- 全地域の一括生成 → 段階導入（日本＋近隣→アジア→他地域）。

## 3. プロフィールの性格

「観光紹介」ではなく「**根拠つきの地域分析レポート**」。読者（太田さん）が①その地域を因果で理解でき、②AIの判断根拠を検証でき、③自分で分析を続ける足場を得られること。投資ポータルの哲学（規律・教育・エビデンス・正直な表示）と同じ思想。

## 4. コンテンツ構造

### 4.1 因果レイヤー（5層＋観光独立枠）

| # | key | 見出し | 中身 |
|---|-----|--------|------|
| 1 | `geography` | 地勢・立地 | 地形/気候/資源/位置（内陸・沿岸・海峡・国境）。全ての土台。 |
| 2 | `economy` | 産業の成り立ちと近代化 | 現在の主要産業＋"なぜここで発展したか"（立地・気候・資源・歴史がどう効いたか）＋**近代化のスピード**（いつ・どれだけ速く・何を契機に）。**既存の「気候・特産・産業」はここに統合**。年表を伴う。 |
| 3 | `society` | 社会・人口 | 人口/民族/言語/宗教/都市化。**固有名で列挙**。 |
| 4 | `geopolitics` | 地政学的位置づけ | 要衝性/隣接関係/海陸/資源ルート/対立の地理的背景。 |
| 5 | `diplomacy` | 外交姿勢と国際的立場 | 現在の（構造的な）スタンス/同盟・対立とその背景。要鮮度。 |
| — | `tourism` | 観光（独立枠） | 見どころ・名物。分析とは別枠の実用情報。都市で厚め。 |

各レイヤーは因果で**つながって**読める（地勢が産業を、産業が社会を、位置が地政を、地政が外交を規定する）。

### 4.2 レベル別の縮退

| レイヤー | 国 `country` | 県/州 `admin1` | 都市 `city` |
|---|---|---|---|
| 1 地勢・立地 | ◎ フル | ◎ フル | ○ 要点 |
| 2 産業＋近代化年表 | ◎ フル＋年表 | ◎ 地域産業の因果＋年表 | ◎ その都市の産業因果 |
| 3 社会・人口 | ○ | ○ | ○ |
| 4 地政学的位置づけ | ◎ 国際的な要衝性 | △ "国内での位置づけ"（国の地政における役割） | △ "国内での位置づけ" |
| 5 外交姿勢 | ◎ フル | ✕（所属国へリンク） | ✕（所属国へリンク） |
| 観光（独立） | ○ | ○ | ◎ 厚め |

地政・外交の主役は**国**。県・都市は**立地・産業因果・近代化**が主役で、地政は「国の地政における"その地域の役割"」に縮退、外交は所属国プロフィールへリンク（`belongs_to`）。観光は都市で厚く。

### 4.3 確度ラベル規則

各レイヤーの主張を3種で明示（本文中のマーカー＋レイヤー末の内訳）：

- `certain`（確実｜地理・事実）：座標・気候区分・人口・産業構成・独立年など、Wikidata/Wikipedia の事実。
- `inferred`（推定｜因果解釈）：「位置＝資源」「立地が発展を駆動」等、**AIの因果解釈**。一次情報ではないことを明示。
- `time_sensitive`（要鮮度｜時事）：外交の現在の動向など、生成時点に依存する事柄。「最新は深掘りで確認」と逃がす。

これは太田さんの④に直接応え、**同時にハルシネーション対策を兼ねる**（弱い根拠を正直に可視化する）。

各レイヤー末に：
- `evidence`（根拠）：AIが何を見てそう述べたか（例「産業構成＝Wikipedia経済節｜発展速度＝一人当たりGDP時系列」）。
- `dig_deeper`（深掘り）：読者が自分で分析するなら次に見る指標・ソース（例「産業別GDP構成／輸出品目」）。

**データ表現**：`body` はプレーン散文とし、確度は `confidence` 配列で構造化保持する。フロントが `confidence` をバッジ/脚注で、`evidence`/`dig_deeper` を末尾ブロックで描画する（付録の「［確実｜地理］」表記は最終的な見え方であり、データ上は `confidence` 配列）。

### 4.4 具体名列挙の原則（生成ルール）

**カテゴリ要約を禁じ、固有名を列挙する**：
- 「4公用語」→「英語・華語（標準中国語）・マレー語・タミル語」
- 「多宗教」→「仏教・キリスト教・イスラム教・道教・ヒンドゥー教」
- 「主要産業」→ 具体的な産業・品目名
- 「隣接国」→ 国名

固有名は可能な限り **Wikidata から事実として供給**（§5.2）し、grounding を強める。字数はほぼ増えない。

### 4.5 近代化タイムライン（年表）

`economy` レイヤーに付随する時系列。近代化のスピード・産業発展の経緯を圧縮的に見せる。

- 各項目 `{year, event, confidence, cause_note}`。年号は原則 `certain`、因果の紐付け（`cause_note`）は `inferred`。
- データ源：Wikipedia 歴史/経済節からの LLM 抽出＋ Wikidata（成立 P571 等）。年号の正確性は実装時に検証（誤年号はハルシネーションリスク）。

### 4.6 外交の鮮度扱い

静的生成（build 時に1回生成→クリック毎コスト0）と鮮度は本質的にトレードオフ。**構造的・恒常的な立場**（例：全方位・等距離外交、非同盟、中立）に軸足を置き、時々刻々の動向は `time_sensitive` ラベル＋ `dig_deeper` へ逃がす。Web 検索・定期再生成は入れない（静的配信の利点を保つ）。`generated_at` を保持し、鮮度の限界を正直に示す。

## 5. 情報源設計

### 5.1 Wikipedia 本文（節抽出）

- 取得：ja Wikipedia action API `action=query&prop=extracts&explaintext&titles={title}` で**全文プレーンテキスト**。
- **関連節だけ抽出**：地理／気候／歴史／経済／産業／政治／対外関係／社会／人口／民族／宗教／交通。
- **除外**：著名人・出身者・スポーツ・教育機関一覧・姉妹都市・脚注・関連項目・外部リンク等の無駄節。
- 入力トークン上限を設定してトリム（コスト制御）。実装で節見出しの分割ロジックとトリム閾値を確定。

### 5.2 Wikidata 地政プロパティ（固有名の grounding）

日本語ラベル（`labels lang=ja`）で取得し、プロンプトに"事実"として構造化して渡す：

| プロパティ | 用途 |
|---|---|
| P37 official language | 公用語名（固有名列挙） |
| P47 shares border with | 隣接国・地域名（地政） |
| P463 member of | 加盟国際機関（ASEAN/UN/EU/NATO/WTO 等・地政/外交） |
| P2132 GDP per capita / P2131 nominal GDP | 所得（近代化・発展度） |
| P1081 HDI | 発展度 |
| P206 located next to body of water | 海・海峡への接続（地政） |
| P571 inception | 成立年（年表起点） |
| P17 country / P131 located in admin / P361 part of | 所属（`belongs_to`） |
| P610 highest point / P2044 elevation / P625 coord / P1082 population / P2046 area | 既存の facts |

宗教構成は Wikidata では弱いので本文由来を主とする。取得は逐次（レート制限・キャッシュ）。

## 6. 出力データスキーマ（JSON v2）

```json
{
  "id": "SG",                         // country=FIPS / admin1=iso_3166_2等 / city=QID（現行踏襲）
  "level": "country|admin1|city",
  "name_ja": "シンガポール",
  "belongs_to": {"level":"country","id":"SG","name_ja":"シンガポール"},  // 県/都市の所属国（外交リンク）。国はnull
  "region_label": "🌏 東南アジア",     // 任意の大分類
  "facts": {"population":5637000,"area_km2":735,"lat":1.3,"lon":103.8,"elevation_m":null,"gdp_per_capita":null},
  "layers": [
    {
      "key": "geography",
      "title": "地勢・立地",
      "body": "本文（因果を語る散文）",
      "confidence": [
        {"label":"certain","kind":"地理","note":"海峡東口の立地・Köppen Af・資源の乏しさ"},
        {"label":"inferred","kind":"解釈","note":"『位置＝資源』という因果読み"}
      ],
      "evidence": "座標/気候＝Wikidata｜要衝性＝位置関係",
      "dig_deeper": ["マラッカ海峡通航量","シーレーン地図"]
    }
    // economy, society, geopolitics, diplomacy（レベルにより縮退/省略）
  ],
  "timeline": [
    {"year":"1819","event":"英・自由貿易港として開港","confidence":"certain","cause_note":"海峡の立地を交易拠点化（推定）"}
  ],
  "tourism": ["マリーナベイ・サンズ","ガーデンズ バイ ザ ベイ","マーライオン","セントーサ島"],
  "source": {"qid":"Q334","wikipedia_url":"https://ja.wikipedia.org/wiki/シンガポール","wikidata_props":["P37","P47","P463","P2132"]},
  "degraded": false,
  "generated_at": "2026-07-04"
}
```

- `degraded`（QID 無し／本文無し／レイヤー皆無）は現行同様、事実のみ表示にフォールバック。
- 後方互換：現行フロントは `sections[{title,body}]` を読む。移行時に `profile_view.js` を新スキーマ対応にする（§10）。

## 7. プロンプト設計

**system**（要旨）：
> あなたは地理・地政学の事典編集者兼アナリストです。与えられた事実（Wikidata）と Wikipedia 本文の抜粋**のみ**を根拠に、地域を「因果の連鎖」で読み解く日本語の分析プロフィールを作ります。規則：(1) カテゴリ要約でなく固有名を列挙（4公用語→言語名／宗教・産業・隣接国も固有名）。(2) 断定は根拠のある事実に限り、因果の解釈は `inferred`、時事依存は `time_sensitive` と明示。(3) 材料に無い情報を創作しない。書けない層は省略してよい。(4) 各層に根拠（何を見たか）と深掘り（次に見る指標）を付す。出力は JSON のみ。

**user**：地域名・レベル・所属・Wikidata 構造化事実（固有名）・Wikipedia 節本文・出力スキーマ指定。

**構造化出力**：Sonnet 4.6 の `output_config.format`（json_schema）対応を実装時に確認。非対応なら**現行の JSON 抽出＋厳格 parse** を踏襲（`parse_profile_response` 相当を新スキーマ用に）。

## 8. モデル・コスト・Batch

- **モデル**：Sonnet 4.6（既定・合意済み／`temperature=0` そのまま）。地政分析の質はパイロットで確認し、必要なら Sonnet 5 を検討（品質↑だが `temperature` 除去＋thinking 無効化のコード変更＋新トークナイザで約30%トークン増）。**オープン事項**。
- **Batch API（50%オフ）**：build 時に対象全件の (Wikidata/Wikipedia 取得 → プロンプト構築) を済ませ、**LLM 呼び出しをバッチ集約**（`messages.batches.create`・custom_id = region id）。取得部（Wikipedia/Wikidata）は逐次＋キャッシュ。結果は custom_id でひも付けて書き出し。
- **コスト概算**（節抽出＋本文＋Sonnet 4.6＋Batch）：入力＝国 ~4-8k / 県 ~1.5-3k / 都市 ~1.5-2.5k トークン、出力 ~1-1.8k。パイロット（日本＋近隣5-6カ国＋県都市＝数百〜1000件）＝**数百〜1000円**。全件（後日）≈ **¥15k前後**。正確値は節抽出後に `count_tokens` で実測。

## 9. スコープと段階導入

- **パイロット**：日本（国1／県47／主要都市）＋近隣（韓国・中国・台湾・シンガポール・タイ 等）とその県・都市の一部。既存の `PROFILE_FIPS` 環境変数で対象国を指定。
- 品質確認（太田さん実機）→ **アジア全体** → 他地域。月ごと。
- 各段階で Batch 生成 → `data/static/profiles/**` 差替 → push（本番反映）。

## 10. 実装への影響（改修範囲）

- `scripts/lib/profile_prep.py`：新スキーマ・節抽出・Wikidata プロパティ拡張・プロンプト刷新・確度/年表/観光・具体名列挙。純関数中心（pytest 対象）。
- `scripts/build_profiles.py`：**Batch API 化**・本文取得（extracts 全文→節抽出）・Wikidata プロパティ fetch 拡張・custom_id ひも付け。
- `js/lib/drilldown/profile_view.js`：新スキーマ描画（layers＋確度バッジ＋evidence/dig_deeper＋timeline＋tourism 独立枠＋belongs_to リンク）。
- `js/lib/drilldown/profile_data.js` / `resolve_place.js`：スキーマ整合。
- CSS：確度バッジ・年表・観光枠のスタイル（面禁則＝不透明フロート内で遵守）。
- テスト：pytest（profile_prep 純関数）／node（profile_view 描画）。

## 11. 検証計画

1. **情報源の実データ検証（workflow）**：日本＋近隣数カ国の 国/県/都市 サンプルで、実際に Wikipedia 本文＋Wikidata から取れる情報の厚みを検証（degraded 率・各層の埋まり具合・固有名の取得可否）。→ 設計が実データで成立するか裏取り（着手前の最初のステップ）。
2. **プロンプト品質検証**：サンプル数十件を実 LLM 生成（数十円）→ 因果の説得力・確度ラベルの妥当性・ハルシネーション有無・具体名列挙を太田さんと確認。
3. **パイロット生成**：日本＋近隣で本生成 → 実機 UI 確認。
4. 単体テスト（pytest/node）緑。

## 12. リスクと対策

| リスク | 対策 |
|---|---|
| ハルシネーション（特に地政・外交・因果） | 確度ラベル（推定/要鮮度）＋「材料のみを根拠」プロンプト＋固有名の Wikidata grounding |
| 外交の鮮度（静的配信で古くなる） | 構造的立場に軸足＋要鮮度ラベル＋深掘りへ逃がす＋`generated_at` 表示 |
| コスト増（本文投入で入力↑） | 節抽出で入力圧縮＋Batch 50%オフ＋段階導入 |
| 小地域の疎さ（本文が短い） | `degraded` 扱い（層省略）＋パイロットで実測 |
| Sonnet 4.6 の構造化出力対応 | 実装時確認、非対応なら JSON 抽出＋厳格 parse |
| 年号の誤り（年表） | Wikidata 由来を優先＋確度ラベル＋実装で検証 |

## 13. オープン事項（実装/パイロットで判断）

- モデル：Sonnet 4.6 vs Sonnet 5（品質 vs コスト/コード変更）＝パイロット品質で判断。
- 構造化出力の可否＝実装時確認。
- 年表のデータ源の主従（Wikipedia 歴史節 LLM 抽出 ／ Wikidata）。
- 確度バッジ・年表・観光枠の UI 表現（実装/デザインで詰める）。
- 節抽出の分割ロジックとトリム閾値。
